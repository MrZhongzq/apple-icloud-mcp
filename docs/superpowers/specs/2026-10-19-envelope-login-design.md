# 远程入口的加密信封登录与访问密钥管理：设计

日期：2026-10-19。状态：草案，待确认。

## 一、为什么做这件事

这件事的起点是 2026-10-19 的部署：远程 HTTP 入口跑在 `https://icloudmcp.zzqhmbb.eu.org`，claude.ai 连接器和 Routine 都已实测跑通。

这种用法要求事先把 iCloud 账号和 App 专用密码写进 VPS 上的 `.env`。这带来两个问题：

1. **无法和朋友共用。** 服务器上只有一套凭据，谁连进来都只能用这一个 iCloud 账号。
2. **凭据离开了主人方便管理的地方。** 改密码、调权限都要登录 VPS 去改 `.env`，再重启容器。

想要的模式是：

- **服务器主人管"谁能连上这台 MCP"**。他给每个人一把访问密钥，每个人用自己的密钥让自己的 claude 连上连接器。
- **每个人管"连上以后用哪个 iCloud 账号、开哪些权限"**。这些写在他自己 Routine 环境里的 `.env` 或环境变量中，和现在的写法一样。VPS 上不预先存任何人的 iCloud 密码。
- **凭据通过加密信封交给服务端。** 运行时，Routine 在沙盒里跑一个脚本，把 `.env` 封装成一个加密信封，并带上一次性 nonce。模型把信封交给 `apple_login`。明文凭据始终不进入对话上下文。

**一个约束决定了信封必须走工具参数。** Routine 里的连接器调用不是从沙盒发出的，而是由 claude.ai 的后端连接 VPS，OAuth 授权也只在浏览器里做一次。沙盒里的 `.env` 无法参与连接握手，所以凭据唯一能走的路是：沙盒脚本输出密文 → 模型把密文作为 `apple_login` 的参数 → 服务端解密。

## 二、目标、非目标、反目标

**目标**

- 远程 HTTP 入口支持用加密信封登录：`apple_login({ envelope })`。
- 访问密钥：每人一把。在 OAuth 授权页上，输入访问密钥取代输入管理员口令。
- 管理页面（WebUI）只做一件事：管理访问密钥。具体包括：
  - 看现在有几把密钥；
  - 看每把密钥上次连接 MCP 的时间；
  - 新建、启用、禁用、销毁密钥。
  - 页面上另外放两样东西：
    - 一个开关，控制是否允许使用 VPS `.env` 里配置的账号；
    - 信封公钥的展示，见第四节。
- 会话与访问密钥绑定。A 的 `session_id` 即使被 B 拿到，B 用自己的密钥也用不了。
- SKILL.md 讲清楚 AI 怎么操作：跑脚本、拿信封、登录、`work_done`。

**非目标**

- **stdio 与沙盒 CLI 两个入口不改动。** 本地运行（Claude 桌面版、Routine 在本机拉起 MCP）直接读 `.env` 登录更快，不需要绕一圈信封。这是用户明确要保留的行为。
- 不做服务端的权限上限。每个人的读写权限完全由他自己的 `ALLOW_*` 决定。
- 不做信封密钥轮换。第一版只生成一次，见「已知风险」。
- 不做多账号信封：一个信封装一个账号。
- 不支持一把访问密钥同时绑定多个人，也不做配额或计费。
- 不修改现有的 OAuth 协议流程本身，包括动态注册、PKCE、刷新令牌轮换和撤销。

**反目标**：出现以下任一情况，即使功能能用，也算失败。

- 明文 App 专用密码出现在对话上下文、工具参数、服务端日志或磁盘上的任何地方。
- 截获的信封可以被重复使用。
- 朋友连进来后，不带信封调用 `apple_login`，就登录进了主人的 iCloud。
- 禁用或销毁一把密钥后，持有者已建立的会话还能继续用。只返回 401 不算数：会话必须从 SessionStore 中消失。
- 现在的本地 stdio 或 CLI 用户升级后需要改任何配置。

## 三、现状与必须改动的地方（已核对代码）

1. **会话没有绑定调用方。** 四个模块的 `tools.ts` 都直接调用 `sessions.get(session_id)` 取会话，`work_done` 也是直接调用 `sessions.destroy(session_id)`。两处都不检查调用方是谁（例如 `src/modules/mail/tools.ts:44`）。只有一个用户时这没有问题；多个用户共用服务器时，`session_id` 就成了唯一凭证。
2. **`loadConfig` 在没有任何账号时直接报错**（`src/core/config.ts:184`）。纯信封部署时，VPS 上没有账号。
3. **工具按账号能力注册。** `registerAllTools` 只注册"至少有一个已配置账号开启了该能力"的模块（`src/server/createServer.ts:28-85`）。没有账号就只剩 session 类工具。service 层已经有按账号能力的检查（`requireRead`/`requireWrite` 一类的函数，位于 `src/modules/*/service.ts`），所以运行时按会话判权限是可以做到的。**构建者需要逐个确认这 25 个工具的每条执行路径都经过这层检查**，因为以后它会成为唯一的权限防线。
4. **OAuth 登录页现在校验的是管理员口令**（`src/auth/login.ts::handleLoginSubmit`），令牌记录（`StoredToken`）里也没有"是哪把密钥签出来的"这一字段。
5. **令牌存储是一份加密快照**（`src/auth/store.ts`），用 AES-GCM 加密，密钥是 `TOKEN_ENCRYPTION_KEY`。快照现在只有 `clients` 和 `tokens` 两部分，可以扩展。

## 四、设计

### 4.1 访问密钥

**数据**：新增在加密快照里，与 `clients`/`tokens` 并列存放。每条记录包含：

- `id`
- `name`：主人起的名字，比如「小明」
- `key_hash`
- `created_at`
- `enabled`
- `last_used_at`

**形状**：

- 明文形如 `amk_<32 字节随机数的 base64url>`。
- 只在新建时显示一次，服务端只存哈希。密钥是高熵随机串，用现有的 `hashToken`（SHA-256）就够了，不需要 scrypt。

**进入 OAuth 流程**：

- 授权页的输入框从「管理员口令」改为「访问密钥」。
- `handleLoginSubmit` 改为按哈希查找密钥，要求找到且 `enabled`。
- 签出的授权码记下 `access_key_id`，由它换出的整族令牌（`StoredToken`）也都带上这个字段。
- 刷新令牌轮换时这个字段沿用不变。

**每次调用 `/mcp` 时**：

- `verifyAccessToken` 额外检查令牌所属的密钥仍然存在且是启用状态，否则返回 401。
- 密钥 id 放进 `AuthInfo.extra`，和现在的 `TOKEN_FAMILY_KEY` 走同一条链路。
- 更新 `last_used_at`。
  - 内存里每次都更新。
  - 落盘要节流，同一把密钥最多每分钟写一次，避免每个请求都重写整份快照。

**禁用**：

- 吊销这把密钥名下的全部令牌族，并销毁这些令牌建立的全部会话，复用现有的 `revokeFamily` 加 `destroyByToken` 配对，或者新增按密钥 id 销毁。
- 密钥记录保留，`enabled=false`。
- 重新启用后可以再次授权；旧令牌已经被吊销，不会复活。

**销毁**：做和禁用一样的切断操作，然后删掉这条记录。

**升级迁移（我的决定）**：

- 升级前由管理员口令签出的令牌没有 `access_key_id`，升级后一律视为无效。
- 主人在管理页给自己建一把密钥，再到 claude.ai 里重新连接一次。
- 这样就不存在"无主"的令牌。

**管理员口令（我的决定）**：从此只用来登录管理页面，不再能用于 OAuth 授权。主人自己也用一把访问密钥。整套模型只有一种授权方式。

### 4.2 管理页面

- **路径**：`/admin`，由服务端渲染 HTML，不引入前端框架。
- **登录**：
  - 使用现有的 `ADMIN_PASSWORD_HASH`。
  - 登录后用 cookie 维持会话：`HttpOnly`、`Secure`、`SameSite=Strict`，空闲 30 分钟过期。会话只存在内存中，进程重启后需要重新登录。
- **防护**：
  - 复用登录页那套响应头 `LOGIN_PAGE_HEADERS`：`no-store`、`X-Frame-Options: DENY`、`frame-ancestors 'none'`。
  - 所有改变状态的 POST 都要校验 `Origin`，必须等于 `PUBLIC_URL` 的 origin。这一条和 `SameSite=Strict` 一起防 CSRF。
  - 登录接口沿用 `/admin-login` 那种按 IP 限流的做法。
- **页面内容**：
  - **密钥表格**：名字、创建时间、状态、上次使用时间，每行有启用/禁用/销毁按钮。销毁需要二次确认，用一个服务端渲染的确认页面，不用浏览器弹窗。
  - **新建**：输入名字，提交后显示一次明文密钥。页面上提示"只显示这一次"。
  - **env 账号开关**：见 4.4。
  - **信封公钥**：以一行文本展示，供主人复制给朋友，见 4.3。
- **路由顺序**：管理路由必须挂在 `mcpAuthRouter` 之前，理由同 `httpApp.ts` 里 `/admin-login` 的注释。

### 4.3 加密信封

**服务端密钥对**：

- 首次启动时生成一对 X25519 密钥，之后保持不变。
- 公钥用 base64url 编码，前面加上版本前缀，例如 `amp1_<…>`，在管理页展示。
- **私钥单独存成一个文件**，不放进令牌快照（我的决定）。
  - 文件与 `TOKEN_STORE_PATH` 同目录，例如 `envelope-key.json.enc`，用同一个 `TOKEN_ENCRYPTION_KEY` 加密。
  - 这样两件事可以互不牵连：
    - 只重建信封密钥对：`rm` 这个文件，然后重启。访问密钥、OAuth 客户端、令牌都不受影响，只是朋友们要换一次 `MCP_ENVELOPE_PUBKEY`。
    - 删除令牌快照：信封密钥对不受影响。
  - `store.ts` 里"解密失败就删文件"的提示要改成分别说明删的是哪一个文件、删了会有什么后果。

**算法**：只用 Node 内置的 `crypto`，零依赖。流程是 ECIES 式的：

1. 客户端生成临时的 X25519 密钥对，与服务端公钥做 ECDH；
2. 用 HKDF-SHA256 派生出 AES-256-GCM 密钥；
3. 加密载荷。

GCM 的附加认证数据（AAD）包含版本号和服务端公钥的指纹。公钥对不上时，服务端能报出明确的错误，而不是笼统的"解密失败"。

**信封格式**：

- 单行字符串，形如 `ame1.<base64url(JSON)>`。
- JSON 内容是 `{ v, kid, epk, iv, ct, tag }`。
- 具体编码细节留给构建者，但必须带版本号，以后才能升级格式。

**载荷（明文部分）**：

```
{
  v: 1,
  nonce: <16 字节以上随机数，base64url>,
  iat: <毫秒时间戳>,
  env: { ICLOUD_ACCOUNT_1, ICLOUD_APP_PASSWORD_1, ICLOUD_SENDER_1?, ICLOUD_LABEL_1?, ALLOW_*_1... }
}
```

**载荷沿用 `.env` 的变量名**：

- 服务端拿到 `env` 后先按白名单过滤，只认 `_1` 后缀的那几个账号变量。
- 然后交给 `core/config.ts` 里现有的 `parseAccount`，构造出 `AccountConfig`。
- 这样所有现有规则自动对信封账号生效：
  - 写权限默认关闭；
  - 布尔值写错就拒绝；
  - iCloud 发信域名保护（非 iCloud 域名时关掉邮件能力）。
- **不允许为信封另写一套解析逻辑。**

**防重放**：

- `iat` 必须落在服务端时钟的 `[now − 5 分钟, now + 1 分钟]` 内。
- nonce 记在内存表里，保留到 `iat + 5 分钟` 之后再清理；同一个 nonce 第二次出现就拒绝。
- 用户最初提的想法是"会话结束后 nonce 作废"。现在 nonce 从第一次使用起就作废，已经覆盖了那个要求。
- 进程重启会清空 nonce 表，见「已知风险」。

**`apple_login` 的变化**：

- 新增可选参数 `envelope`，与 `account` 互斥。
- 带 `envelope` 时：
  1. 解密，校验时间窗和 nonce；
  2. 解析出 `AccountConfig`；
  3. 和现在一样，按能力验证所需协议；
  4. 建立会话。账号只存在于这个会话里，不写入 `config.accounts`，也不落盘。
- 失败时一律返回 `INVALID_INPUT`，`hint` 按原因区分：
  - 过期或重放 → 重新运行脚本生成新信封，再试一次；
  - 公钥对不上 → 让服务器主人提供当前公钥，更新 `MCP_ENVELOPE_PUBKEY`；
  - 格式或解密错误 → 同上。
- **信封内容、解密后的载荷，一律不进日志**；日志只记失败原因的类别。

**`apple_accounts`（我的决定）**：只列 env 账号。env 账号开关关闭时返回空数组。tool description 和 SKILL.md 里说明"远程信封模式下这里为空是正常的"。

### 4.4 env 账号开关

- 存在加密快照的设置里，在管理页切换，**默认关闭**。
- 关闭时：
  - `apple_login` 只接受信封，带 `account` 或什么都不带都返回明确的错误；
  - `apple_accounts` 返回空数组。
- 打开时：恢复现在的行为，`.env` 里的账号可以用 `account` 登录。
- **打开后，任何一把有效密钥都能登录 env 账号**（我的决定）。这是单人部署的兼容模式，管理页在开关旁边写明这一点。按密钥分配 env 账号的功能不做。
- 启动时如果 `.env` 里配了账号而开关是关的，打一条警告日志，提醒"这些账号当前不可用"。

**部署影响**：VPS 上现在的 `.env` 里还有账号。升级后开关默认关闭，这些账号立刻不可用。主人计划清掉它们，所以这正是预期行为，但升级说明里要写清楚。

### 4.5 会话绑定

- `Session` 增加 `ownerKeyId?: string`。`apple_login` 从 `extra` 里取出密钥 id 写进去，取法同 `tokenFamilyIdFrom`。
- **会话归属只在一个地方检查**：`SessionStore.get` 和 `destroy` 增加调用方身份参数，归属不匹配时返回 `SESSION_EXPIRED`（不返回 `PERMISSION_DENIED`，以免泄露"这个 id 存在"）。四个模块的 `serviceOf` 和 `work_done` 都把 `extra` 里的身份传进去。
- **stdio/CLI 入口**：建会话时 owner 为 undefined，调用方的身份也是 undefined，比较时两者相等，所以这两个入口的行为不变。
- **禁用/销毁密钥**：按 owner 销毁会话，或者按这把密钥名下的全部令牌族销毁。具体用哪种由构建者决定，但必须做到"会话从 SessionStore 中消失"。
- **`work_done` 归属不匹配时**：表现与"会话不存在"完全相同，返回 `success: false`，不销毁任何东西。
- **MCP 传输层也绑定密钥（我的决定）**。
  - `httpApp.ts::createMcpRouteHandler` 的 `entries` 表按 `mcp-session-id` 存放 transport。
  - 不加检查的话，B 拿到 A 的 `mcp-session-id` 后，可以用自己的令牌对它发 `DELETE`，关掉 A 的连接，或者在上面挂 SSE 流。
  - 做法：
    - `McpEntry` 在 initialize 时记下密钥 id；
    - 之后每个请求比对，不匹配就按"会话不存在"处理（400/404，与现在缺 id 的处理一致）；
    - 禁用或销毁密钥时，一并关闭这把密钥名下的 transport。
  - 这是另一层资源上的检查，iCloud 会话的归属检查仍然只在 `SessionStore` 里做一处。
- **关闭 env 账号开关时**：已经用 env 账号建立的会话一并销毁。
- **授权码兑换时**（`exchangeAuthorizationCode`）：再检查一次密钥是否仍然启用。用户在登录页输入密钥之后、claude.ai 来兑换授权码之前，密钥可能已经被禁用。

### 4.6 工具注册与配置加载

- **HTTP 入口**：
  - `loadConfig` 增加一个选项，允许零账号，由 `bin/http.ts` 传入；stdio/CLI 不传，继续在零账号时报错。
  - 不论 env 有没有账号，`registerAllTools` 一律注册全部 25 个工具，权限交给 service 层按会话的账号去判断。
  - 实现方式可以是给 `registerAllTools` 加一个"全部注册"的选项。
- **stdio 和 CLI**：保持按账号能力注册，行为完全不变。

### 4.7 客户端脚本 `scripts/make-envelope.mjs`

- 零依赖，要求 Node ≥ 20，风格与 `scripts/probe-network.mjs` 一致。
- **输入**：
  - 优先读进程环境变量，因为云端 Routine 环境通常把凭据设成环境变量；
  - 也可以用 `--env-file <path>` 指定一个 `.env` 文件。
  - 服务端公钥从 `MCP_ENVELOPE_PUBKEY` 读取。
  - 只读 `_1` 账号。如果配置了 `_2` 及以上，拒绝并退出，理由同 CLI 拒绝多账号。
- **输出**：
  - stdout 只输出一行信封，什么都不多输出；
  - 出错写 stderr，只说缺了哪个变量名，绝不打印任何变量的值；
  - 退出码：0 表示成功，1 表示失败。
- **不联网**：公钥来自本地配置。云沙盒在受限网络下未必能访问服务器域名，脚本不应依赖这一点。

### 4.8 SKILL.md 与文档

**SKILL.md**：

- 「Which of these are you?」部分增加第三类读者：远程连接器，同时手里有 shell 和仓库。
- 流程：
  1. 运行 `node scripts/make-envelope.mjs`，把它的 stdout 原样作为 `apple_login` 的 `envelope` 参数，不要打印、不要改动；
  2. 正常调用工具；
  3. 最后 `work_done`。
- 遇到过期或重放的 `INVALID_INPUT`，重新生成一次再试，只试一次。
- 不要读或打印 `.env`（沿用现有规则）。

**部署文档 `docs/部署与-Routine-接入.md`**，补充以下内容：

- 主人：部署服务、进入管理页、建密钥、复制公钥给朋友。
- 朋友：
  1. 拿到访问密钥和公钥；
  2. 在 claude.ai 添加连接器，用密钥完成授权；
  3. 在 Routine 环境里配置 `.env` 或环境变量，加上 `MCP_ENVELOPE_PUBKEY`；
  4. Routine 拉取仓库、读取 SKILL.md。
- **信任说明**：朋友的 App 专用密码会在主人的 VPS 内存里以明文形式存在，直到会话结束。朋友必须信任服务器主人。

**同批补上之前积压的几项文档**：

## 五、安全分析

**能保护的**：

- VPS 磁盘上不存放任何 iCloud 密码。
- 对话记录里只有密文。
- 截获的信封在 5 分钟后失效，在 5 分钟内也只能用一次。
- 每个人只能用自己的会话。
- 撤销一个人不影响其他人，而且是当场切断。

**不能保护的（必须写进文档）**：

- **VPS 能看到明文。** 它要代替你连接 iCloud，所以会话期间密码在 VPS 内存里是明文。服务器主人，或者攻破了 VPS 的人，可以读到所有活动会话的密码。
- **私钥加上截获的信封等于密码。** 信封私钥存在加密快照里，解密快照的 `TOKEN_ENCRYPTION_KEY` 也在同一台机器的 `.env` 里。如果有人同时拿到 VPS 的磁盘和某段对话记录里的信封，即使信封早已过期，他也能解出里面的密码。缓解办法：
  - 第一版不做轮换；
  - 万一 VPS 泄露，所有朋友都应该到 appleid.apple.com 重新生成 App 专用密码。主人需要重建密钥对：删除 `envelope-key.json.enc` 后重启，再把新公钥发给大家。
  - 这一点写进部署文档。
- **进程重启会清空 nonce 表。** 重启前 5 分钟内签发的、已经用过的信封，在重启后剩余的时间窗内可以再被用一次。前提是攻击者同时持有一把有效的访问密钥，因为 `/mcp` 先要过 OAuth。这个风险可以接受，写进文档即可。

## 六、测试要点（必须是能区分对错的测试）

- **会话归属**：用真实的 provider、store、SessionStore，监听真实端口，两把密钥 A 和 B。A 调 `apple_login`，B 拿 A 的 `session_id` 调用任意工具，结果必须是 `SESSION_EXPIRED`；B 调 `work_done(A 的 id)`，A 的会话必须仍然存在。
- **禁用密钥**：断言会话从 SessionStore 中消失。只断言 `/mcp` 返回 401 不算，原因见 CLAUDE.md 里关于撤销的那条约束。
- **重放**：同一个信封第二次调用 `apple_login` 被拒；`iat` 超出时间窗被拒；拿另一套密钥对的公钥加密的信封报"公钥不匹配"，而不是笼统的错误。
- **信封与 env 规则一致**：
  - Gmail 地址的 Apple ID 封进信封，邮件能力必须被关闭；
  - `ALLOW_MAIL_WRITE_1` 缺省时写权限是 false；
  - 布尔值写错时登录失败。
  - 这几条测试的固定数据本身不能带有被测属性，避免测试形同虚设。
- **脚本**：
  - 用子进程跑真实的 `make-envelope.mjs`，拿输出交给服务端解密，必须得到原值；
  - 断言脚本的 stdout 和 stderr 都不包含密码明文，包括出错路径。
- **env 开关**：关闭时，不带信封调用 `apple_login` 必须失败，即使 `.env` 里有账号也一样。这是"朋友登进主人 iCloud"那个反目标的直接测试。
- **零账号启动**：HTTP 入口在没有账号时能启动，并且注册了 25 个工具；stdio 在零账号时仍然报错。
- **旧令牌**：升级前签发、不带 `access_key_id` 的令牌，访问 `/mcp` 返回 401。
- **管理页**：
  - 未登录访问一律跳转登录；
  - POST 带错误的 `Origin` 被拒；
  - 新建密钥后，列表和磁盘快照里都只有哈希。

## 七、我替你做的决定（请过目）

1. 管理员口令不再能用于 OAuth 授权，主人自己也用访问密钥。
2. 升级前签发的令牌全部作废，需要重新连接一次。
3. env 账号开关默认关闭；打开时所有密钥都能使用 env 账号。
4. 信封时间窗为过去 5 分钟、未来 1 分钟。
5. 服务端公钥由主人手动复制给朋友，写进朋友的 `MCP_ENVELOPE_PUBKEY`，脚本不联网获取。
6. 信封载荷沿用 `.env` 的变量名，服务端复用 `parseAccount`。
7. 归属不匹配时报 `SESSION_EXPIRED`，不报 `PERMISSION_DENIED`。
8. 客户端脚本用 Node 写，不用 Python，因为 Python 标准库没有公钥加密。
9. 第一版不做信封密钥轮换按钮。私钥单独存一个文件，删掉它再重启就是重建。
10. MCP 传输层（`entries` 表）也按密钥做归属检查；禁用密钥时连同 transport 一起关闭。
11. 关闭 env 开关时，销毁已有的 env 账号会话；兑换授权码时再检查一次密钥是否启用。
12. `envelope` 参数只出现在 HTTP 入口的 `apple_login` 上，stdio 和 CLI 不暴露。
13. 信封会话遇到 `PERMISSION_DENIED`（能力关闭）时，hint 改成"在你自己的 `.env` 里把 `ALLOW_…_1` 设为 true，重新生成信封后再登录"，不再写"重启服务"。
