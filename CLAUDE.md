# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

`apple-icloud-mcp`: an MCP server exposing Apple iCloud Mail (IMAP/SMTP), Calendar (CalDAV), Reminders (CalDAV VTODO), and Contacts (CardDAV) as tools. TypeScript, ESM (`"type": "module"`, `module: NodeNext`), `strict` + `noUncheckedIndexedAccess` on. Phase one shipped Mail + Calendar; phase 2a added Reminders; phase 2b added Contacts — all four modules are in this repo now. Phase three added a second entrypoint: alongside the original **stdio** transport (`src/bin/stdio.ts`, a local subprocess for a single trusted client), `src/bin/http.ts` serves the same 25 tools over **remote Streamable HTTP**, fronted by a self-hosted OAuth 2.1 authorization server (`src/auth/`) and an Express app (`src/server/httpApp.ts`). Phase four added a **third** entrypoint, `src/bin/cli.ts`: a command line over the same tools, for a Claude Routine that has a sandbox shell but cannot launch a local MCP subprocess or reach a remote connector. All three entrypoints share `src/modules`, `src/providers`, and `src/parsers` unchanged — each new entrypoint is additive, not a fork. Deployment artifacts (`Dockerfile`, `docker-compose.yml`, `Caddyfile`) and remote-deployment docs live at the repo root and in `README.md` → "Remote deployment"; the sandbox CLI is documented in `docs/沙盒-CLI-用法.md`.

## Commands

```bash
npm start               # dev: tsx runs src/bin/stdio.ts directly, no build step
npm run build            # tsc -> dist/
npm run serve             # prod: node dist/bin/stdio.js (requires a prior build)
npm run cli -- --list     # sandbox CLI: list the 23 CLI commands (requires a prior build)
npm run typecheck         # npx tsc --noEmit
npm test                  # unit suite: vitest.config.ts, tests/unit/**, no network
npm run test:integration  # live-iCloud suite: vitest.integration.config.ts, tests/integration/**
                           # skipped entirely unless .env.test exists at repo root
```

`npx vitest run` (no config flag) runs the unit config and therefore never touches real iCloud. The integration suite is opt-in only — see `README.md` → Testing.

## Architecture

Strict layering, request path `bin → server → modules → providers`, with `parsers` as a separate pure-function layer consumed by `modules`:

- **`src/core/`** — cross-cutting, no I/O of its own. `config.ts` is the single source of credentials: `loadConfig(env)` scans `ICLOUD_ACCOUNT_1..5` etc. and builds `AccountConfig[]`, mapping legacy lowercase v1 variable names with a deprecation warning. `errors.ts` defines `AppError`/`ErrorCode` and `toErrorPayload()`, the only thing that ever crosses the tool boundary on failure. `session.ts` is an in-memory `Map`-backed session store (TTL-based expiry, swept periodically). `ids.ts` encodes/decodes opaque resource ids as base64url.
- **`src/providers/icloud/`** — thin wrappers around `imapflow`, `nodemailer`, and `tsdav`, one file per protocol plus `index.ts` (`createProviders`) that assembles all three for a session. Each provider maps raw client errors to `AppError` via a local `mapXError()` function (`mapImapError`, `mapSmtpError`, `mapCalDavError`). No knowledge of MCP or tool schemas belongs here.
- **`src/parsers/`** — pure functions, no I/O: `mime.ts` decodes MIME/RFC 2047 email content, `ical.ts` converts between iCal text and both the `CalendarEvent`/`EventInput` (VEVENT) and `Reminder`/`ReminderInput` (VTODO) domain types (parsing, building, patching, recurrence expansion), `vcard.ts` converts between vCard text and the `Contact`/`ContactInput` domain types the same way. Because they're pure, these are the easiest layer to unit test exhaustively and where most of the calendar/reminder/contacts edge-case tests live (`tests/unit/parsers/ical*.test.ts`, `tests/unit/parsers/vcard*.test.ts`).
- **`src/modules/{mail,calendar,reminders,contacts,session}/`** — one module per domain, each split into `service.ts` (business logic: permission gates, calls into providers/parsers, maps to response shapes) and `tools.ts` (zod input schemas + `registerTool` wiring; thin — delegates straight to the service). `contacts` additionally has `cache.ts` (the session-scoped search cache — see below).
- **`src/server/`** — `createServer.ts` builds the `McpServer` and calls each module's `register*Tools`, gated on whether *any* configured account has that capability at all (an account-level filter, not per-call). `wrap.ts` is the tool boundary: serializes success as JSON text, catches anything and turns it into the `{ error: {...}, isError: true }` shape via `toErrorPayload`. `types.ts` defines the minimal `ToolRegistrar` interface the modules depend on, so tool-registration logic can be unit-tested without booting a real `McpServer`.
- **`src/bin/stdio.ts`** — the original entrypoint (see `src/bin/http.ts` and `src/bin/cli.ts` for the other two). Loads config, builds the session store and server, connects a `StdioServerTransport`, installs `SIGINT`/`SIGTERM` handlers with a bounded shutdown timeout. Any startup failure (bad config, etc.) writes to **stderr** and exits non-zero — never stdout.
- **`src/cli/`** — the CLI entrypoint's own layer, nine files, consumed only by `src/bin/cli.ts`. `registry.ts` is a third `ToolRegistrar` that collects tools into a `Map` instead of registering them with an `McpServer`; `flags.ts` derives each command's flags and `--help` from the tool's own zod schema; `execute.ts` runs one call in an implicit session; `batch.ts` runs a list of ops in one session; `transport.ts`/`daemon.ts`/`client.ts`/`start.ts` are the session-reusing daemon. `invokeTool` (in `execute.ts`) is the single choke point all three call paths share — one-shot, batch, and daemon.

`SKILL.md` is the usage contract an AI client reads (login → call with `session_id` → `work_done`, all 25 tools, error-code recovery table). **Adding or changing a tool touches at least three places**: the module's `tools.ts` (schema + registration), the module's `service.ts` (behavior), and `SKILL.md` (the contract — which now addresses two readers, an MCP client and a CLI caller, and must stay coherent for both). It touches **no** CLI code: `src/cli/registry.ts` re-runs the same `registerAllTools`, and flags are derived from the schema, so a new tool becomes a command automatically. The only CLI decision is whether it belongs in the 23. If it changes a documented limitation (see README's "Limitations" section), update the README too.

## Non-obvious constraints and why

- **ESM relative imports need an explicit `.js` extension**, even though the source files are `.ts` (`import { X } from '../core/config.js'`). This is `NodeNext` module resolution, not a typo — TypeScript resolves it to the `.ts` file at compile time but the emitted JS needs the extension to run.
- **stdout belongs entirely to the MCP protocol.** Nothing in this codebase writes to stdout directly; all logging goes through `core/logger.ts` to **stderr**, and startup failures in `bin/stdio.ts` are written to stderr explicitly. Never add a `console.log` — it would corrupt the stdio JSON-RPC stream.
- **IMAP/SMTP authenticate with `account.sender`; CalDAV authenticates with `account.email`.** These are two different fields on `AccountConfig` (`sender` falls back to `email` if `ICLOUD_SENDER_n` isn't set) because a user's IMAP/SMTP login identity can be an alias distinct from their Apple ID, while CalDAV always wants the Apple ID. This exact confusion caused real bugs in the v1 history (`Fix IMAP auth`, prior `Fix icloud email sender logic`) — when touching auth code in `providers/icloud/*.ts`, keep the two straight. It also caused a real misdiagnosis: an Apple ID that's a Gmail address falls back `sender = email`, Apple's IMAP server rejects a non-iCloud username outright, and the resulting `AUTHENTICATIONFAILED` looks exactly like a revoked App-Specific Password. `core/config.ts::loadConfig` now guards against this at config-load time: after parsing each account, if its effective `sender` isn't on an iCloud mail domain (`icloud.com` / `me.com` / `mac.com` / `icloud.com.cn`, exact-match on the domain — not a suffix check), that account's `mailRead`/`mailWrite` are forced to `false` regardless of `ALLOW_MAIL_*`, and an explanatory string is pushed onto `AppConfig.notices` (printed to stderr by `bin/stdio.ts`, alongside but separate from `deprecations`). Calendar capabilities are untouched — a calendar-only user on a non-iCloud address is unaffected. Don't "fix" this by relaxing or removing the domain check; it exists specifically because the fallback-to-email behavior above is otherwise a silent trap.
- **Write permissions default to OFF** (`ALLOW_MAIL_WRITE_n` / `ALLOW_CALENDAR_WRITE_n` / `ALLOW_REMINDERS_WRITE_n` / `ALLOW_CONTACTS_WRITE_n`), while read defaults to ON. This was deliberately flipped from v1, where write defaulted to on and a misspelled variable name silently granted delete access. `core/config.ts::readBool` takes an explicit `fallback` per call — don't change a write-capability default to `true` without a very good reason and a note in the README.
- **CalDAV etags never appear in a tool's public interface.** `expected_etag` is an *optional* optimistic-concurrency input a caller may supply, but `event_id`/`calendar_id` (built by `core/ids.ts`) never encode an etag, and no tool response surfaces one. Etags are read fresh from CalDAV (`loadForWrite` in `modules/calendar/service.ts`) immediately before every write and compared there — never trust or thread through a cached one.
- **`calendar_update_event` patches the existing VEVENT in place; it does not rebuild it from the `CalendarEvent` model.** `parsers/ical.ts::applyEventPatch` mutates the parsed iCal AST for only the fields present in the patch. This is deliberate: rebuilding from the domain model would silently drop every iCal property our model doesn't represent — `ATTENDEE`, `ORGANIZER`, `CATEGORIES`, `STATUS`, `X-APPLE-*` — which is real user data (invitee lists, RSVP state) this phase does not manage. The model is still used to *validate* the merged result (e.g. `end` after `start`) before the patch is written.
- **Event creation has no `timezone` field and never will in this phase** (`EventInput` in `parsers/ical.ts`). Emitting `DTSTART;TZID=` correctly requires shipping VTIMEZONE data this phase doesn't have, so created events are UTC-anchored; a recurring event drifts an hour across a DST transition for zones that observe it. This is documented in the README/SKILL, not a bug to silently "fix" by adding a timezone parameter without also solving VTIMEZONE.
- **All-day dates are read out of the ISO string's own fields, never off a `Date`.** `parsers/ical.ts::toIcalTime`'s all-day branch takes Y/M/D by regex from the leading `YYYY-MM-DD` of the input, because that part is already written in the offset the caller supplied. It used to build `ICAL.Time.fromJSDate(date, true)` and read Y/M/D off the UTC rendering, which silently shifted the date by a day for any offset straddling midnight: `2026-09-01T00:00:00+08:00` wrote `DATE:20260831` and `2026-09-01T23:00:00-05:00` wrote `DATE:20260902`. SKILL.md tells callers to send explicit offsets, so that was the *expected* input shape, and it hit both event `all_day` and reminder `all_day_due` (they share this function). Don't "simplify" this back into a `Date` round-trip — it also makes the result depend on the host machine's timezone, which `tests/unit/parsers/ical-allday.test.ts` exists to prevent.
- **`core/ids.ts` and `providers/icloud/caldav.ts` must stay domain-neutral in what they say.** Neither can know which tools `createServer` actually registered — an account can have calendar off and reminders on, or contacts only. `caldav.ts` is shared by calendar and reminders; `ids.ts::decodeUrl` is shared by **three** domains, since `modules/contacts/service.ts` decodes `address_book_id` through it too. So their error messages use 资源 / 集合, not 日历 / 事件, and any recovery hint names a listing tool for *every* domain that calls in — `decodeUrl`'s hint names `calendar_list`, `reminders_lists` **and** `contacts_search`. A hint naming too few tools has now been shipped-and-fixed three times (once in `reminders_list_lists`, twice here), so `tests/unit/core/ids.test.ts` no longer hard-codes the list: it scans `src/modules/*/service.ts` for actual `decodeUrl` callers and requires the hint to name each one's listing tool. Add a fourth consumer and that test tells you to register its tool rather than silently passing.
- **Calendar privilege detection fails safe, not closed.** `providers/icloud/caldav.ts::applyPrivilegeFallback`: if `current-user-privilege-set` detection finds *no* writable calendar at all across the account, every calendar is reported `writable: true` rather than `false` — because iCloud accounts always have at least one genuinely writable calendar, so an all-read-only result more likely means detection broke than that the account can't write anywhere. The server's own 403 handling (`mapCalDavError`) is the real backstop in that case, not the `writable` flag.
- **`mail_delete` moves to trash by default; only `permanent: true` expunges.** Don't assume delete is immediate/irreversible unless that flag is set.
- **`parsers/vcard.ts` uses `ical.js` for vCard, not a dedicated vCard library.** iCloud's CardDAV responses are vCard 3.0; the one vCard-specific package this project could otherwise add, `vcard4`, only implements 4.0 and would not parse what the server actually gets back. `ical.js` already ships in this repo for `parsers/ical.ts` and its `ICAL.Component`/`ICAL.Property` AST is format-agnostic enough to build and parse vCard 3.0 too, so reusing it costs zero new dependencies. Don't "upgrade" to a dedicated vCard package without first checking it actually handles 3.0.
- **The contacts search cache (`modules/contacts/cache.ts`) lives on `Session`, not at module scope.** `createContactsCache()` is called lazily per-session in `createServer.ts` (`session.contactsCache ??= …`) rather than once when the contacts module is registered. A module-scoped cache would be shared by every session past and future; phase three's remote transport brings concurrent sessions (possibly different accounts), and a shared cache would leak one tenant's contacts into another's search results. Keep any future contacts state on `Session`, the same place `contactsCache` already lives.
- **`AddressBookInfo.readOnly` is always `false`.** `providers/icloud/carddav.ts::listAddressBooks` does no privilege discovery the way CalDAV does (`current-user-privilege-set` / `applyPrivilegeFallback`) — every address book reports `readOnly: false`, and the real backstop is the 403 a write gets mapped through `mapCardDavError`. `modules/contacts/service.ts`'s read-only check on `AddressBookInfo.readOnly` is consequently dead code under the current provider, kept deliberately so that adding real discovery later is a provider-only change with no service-layer edit required.
- **The HTTP entrypoint keeps one `StreamableHTTPServerTransport` + `McpServer` pair per MCP session, never a module-level singleton — and that map needs a sweeper, because it does not shrink on its own.** `src/server/httpApp.ts::createMcpRouteHandler` keys a `Map` by MCP session id and creates a fresh transport/server pair on each `initialize`. This exists specifically because v1's stdio-only design had a single transport per process, which was safe only because stdio serves exactly one client per process; naively reusing that shape for a shared HTTP process would mean a second client connecting evicts the first client's transport out from under it — the single highest-priority defect this phase's review process flagged in the v1 lineage. Any future change to how `/mcp` is wired must keep this per-session, not go back to a shared instance for "simplicity." The other half is disposal: `transport.onclose` only fires when a client closes properly (a `DELETE`, or the connection ending), so a client that just drops and reconnects leaks a transport plus an `McpServer` on every attempt, for the process lifetime. Each entry therefore carries a `lastActiveAt` refreshed on every request, and `sweepIdleTransports` — called from `bin/http.ts`'s existing timer alongside `sessions.sweep()` and `provider.sweep()` — closes and removes anything idle past `config.sessionTtlMs`. It reuses the session TTL deliberately rather than introducing a second knob: an entry in this map *is* "a client still using the server", judged by the same standard the `SessionStore` uses. Note the entry object stored in the map must be the same object the request path mutates — an earlier version put a separate literal in via `onsessioninitialized`, and a second object would mean the sweeper reads a `lastActiveAt` nobody refreshes.
- **`TRUST_PROXY` is off by default and the shipped `docker-compose.yml` turns it on.** Rate limiting (`/admin-login` here, plus the SDK's own limits on `/token`, `/register`, `/revoke`) buckets on `req.ip`, and what `req.ip` means depends entirely on express's `trust proxy`. Both settings are wrong in the other's deployment, so this is configuration, not a default to guess at: with the port exposed directly, `X-Forwarded-For` is written by the caller, and trusting it lets anyone pick their own bucket and retry the admin password without limit; behind the Caddy container this repo ships, *not* trusting it means every request arrives from one container IP, per-IP limiting distinguishes nobody, and one unauthenticated visitor can exhaust the admin-login and `/token` budgets for everyone — locking the entire authorization flow, not just their own access. `core/config.ts::loadHttpConfig` reads it (default `false`), `httpApp.ts` applies it as the very first thing on the app, and `docker-compose.yml` sets `TRUST_PROXY: "true"` with a comment explaining that it is safe there only because nothing but `caddy` can reach `app`.
- **Revoking a token must destroy the MCP sessions it authorized, not just the token record.** `src/auth/provider.ts::revokeToken` calls `store.revokeByToken` (removes the token family from the auth store) and then, unconditionally when a family was found, `sessions.destroyByToken(familyId)`. Deleting only the auth-store record and leaving the `SessionStore` alone would mean a revoked client keeps working against `/mcp` until its in-memory session independently expires — taking away the ticket while leaving the holder still in the room. The same pairing has to hold for refresh-token-replay handling (`exchangeRefreshToken`'s reuse-detection branch), which revokes the family *and* destroys its sessions for the same reason: a replayed refresh token is a leak signal, and the leaked session must die with the token, not outlive it. **That pairing only works because the family id is threaded end to end, through three places that are easy to break independently**: `verifyAccessToken` puts it on `AuthInfo.extra` under `TOKEN_FAMILY_KEY` (`core/session.ts` owns that constant, so the writer in `auth/` and the reader in `modules/` can't drift apart); `server/wrap.ts::wrapTool` forwards the SDK's *second* callback parameter (`RequestHandlerExtra`) to the handler; and `apple_login` reads it with `tokenFamilyIdFrom(extra)` and passes it as `sessions.create(account, familyId)`. Break any one link and every session gets `tokenFamilyId: undefined`, `destroyByToken`'s filter matches nothing, and both revocation paths silently become no-ops — which is exactly what shipped once, undetected, because three unit tests each mocked the link they were meant to exercise. The test that actually holds this property is in `tests/unit/server/http-e2e.test.ts`: real provider, real store, real session store, real port, `apple_login` called through `/mcp`, and the assertion is that the session is *gone from the session store* after `POST /revoke`. Never accept "`/mcp` returns 401 afterwards" as evidence for this: that is `verifyAccessToken` rejecting a deleted token record at the HTTP boundary, and it is true even when zero sessions are destroyed.
- **`ICAL.TimezoneService` is registered and torn back down around every parse/patch call, never left registered.** `src/parsers/ical.ts::withTimezones` snapshots whatever was registered under each VTIMEZONE's TZID before the call, registers this document's own definition for the duration of `fn()`, and restores the snapshot (or removes the entry if there was none) in a `finally`. This isn't cleanup fastidiousness: `ICAL.TimezoneService` is a single process-wide table keyed only on the TZID string, ical.js consults it from inside its own parsing path with no way to intercept that, and the HTTP entrypoint runs one process serving concurrent sessions across potentially different accounts. Leaving a registration in place after the call that added it would let one tenant's VTIMEZONE definition silently govern a *different* tenant's later parse of the same TZID — wrong, and wrong with no trace of why. Register-per-call-and-restore is the only isolation available without forking ical.js; see the full rationale in `ical.ts` above `withTimezones` and `tests/unit/parsers/ical-timezone-isolation.test.ts`.
- **VTODO and VEVENT share one parsing layer but use opposite collection-membership rules, on purpose.** `modules/reminders/service.ts::todoLists` filters CalDAV collections with `c.components.includes('VTODO')` — strict, no fallback. `modules/calendar/service.ts::listCalendars` filters with `c.components.length === 0 || c.components.includes('VEVENT')` — a collection that declared no `components` at all is still treated as usable for events. These look inconsistent but aren't: a calendar collection with an absent/empty `supported-calendar-component-set` is a real thing iCloud returns for some legacy/default calendars, and the safe assumption there is "this is an ordinary event calendar" (VEVENT is what a bare calendar means if nothing says otherwise). A VTODO list, by contrast, is never the default — it only exists because something explicitly declared `VTODO` support — so there is no equivalent "assume it's a reminder list" fallback to make, and treating an unlabeled collection as a reminder list would wrongly pull ordinary calendars into `reminders_lists`. Don't "fix" this by making both sides match; that would either start missing legitimate unlabeled calendars or start misclassifying them as reminder lists.

- **The CLI is a third `ToolRegistrar`, and every input it accepts is derived from the tools' own zod schemas — never hand-written.** `src/cli/registry.ts` re-runs `registerAllTools` against a collector, so all tools are reachable with no per-tool CLI code, and `flags.ts` builds both the flags and `--help` from each `inputSchema`. Hand-writing a flag parser per tool would be that many places to drift from the schema. Corollary: a `nullable` field maps to `--unset-<key>`, which today applies to **zero** tools — every three-state field lives inside a `--patch <json>` blob rather than at the top level. The machinery is kept deliberately: delete it and a future top-level three-state field silently has no way to be cleared.
- **`apple_login` and `work_done` are excluded from the CLI by name, and that name list is correct.** The CLI owns the session lifecycle — a session is the process (one-shot) or the daemon (reusable) — so exposing them lets a caller `cli work_done` and read `{"success": true}` while what was destroyed is the empty session the CLI just made for it. This is not in tension with `execute.ts` deciding session need by `'session_id' in inputSchema` rather than a name list: the test is **whether the schema can express the constraint**, not whether name lists are bad. Session need is a schema fact; "the CLI owns this tool's lifecycle" is not. The exclusion must be applied on **every** entry path — single dispatch and `batch` alike; batch bypassing it resurrects the exact bug.
- **The CLI validates arguments against each tool's own schema in `invokeTool`, because the MCP SDK's validation does not run on this path.** stdio and HTTP get input validation for free — the SDK checks `inputSchema` before invoking a handler — while the CLI calls handlers directly. The handlers were written assuming that check happened. Validation therefore lives at `invokeTool`, the one point one-shot, batch and daemon all pass through; putting it in `executeOnce` alone would leave every command after `cli start` unvalidated, making the precondition depend on whether a daemon is running. It uses `z.strictObject(tool.config.inputSchema)` — the same schema, not a copy — runs **after** `session_id` injection so the injected value is checked too, and rejects unknown keys rather than stripping them. A schema violation is exit **1** (the tool never ran), which is why `ToolArgsError` is tagged across the daemon wire: otherwise the same bad command exits 1 or 2 depending on whether `cli start` was run.
- **Batch validates the whole op list before executing anything**, and the property is *not* "it throws" — validate-as-you-go throws too, just later. It is that ops 1–2 have not already had their side effects when op 3 turns out to be a typo. Any test for this has to assert nothing ran, not merely that an error surfaced.
- **CLI stdout carries only the result JSON**, exactly as stdout belongs to the protocol under stdio; logs and errors go to stderr, and `src/` has no `console.log`. Exit codes are load-bearing and distinct: 0 success, 1 the CLI itself failed (bad arguments, unknown command, missing config — the tool never ran), 2 the tool ran and returned a structured error. A caller can retry a 2 with different arguments; retrying a 1 is pointless.
- **The daemon's socket permissions are the entire access control, so the runtime directory is per-uid and forced to 0700 — in two steps, because one is not enough.** Behind that socket sits a logged-in session holding live iCloud connections. `mkdir`'s `mode` closes the window between creating the directory and chmod-ing it (a real regression shipped through exactly that window), but `mkdir(recursive)` is a **no-op on a directory that already exists, mode included** — and `MCP_CLI_RUNTIME_DIR` is a documented knob pointing at exactly such a path — so `ensureOwnedDir` verifies ownership and then `chmod`s to 0700 as well. Removing either half leaves a real configuration unprotected. The socket is `chmod 600` after `listen` as defence in depth, and ownership is verified before `listen`, not after. Windows blocks unix sockets, so the TCP fallback carries a handshake token from a 0600 file — on POSIX both transports reduce to "can you read that file"; **on Windows neither the mode nor the ownership check does anything** (Node maps `mode` to the read-only attribute and there is no `getuid`), and the only real boundary is the per-user ACL on `%TEMP%` — which a `MCP_CLI_RUNTIME_DIR` pointing somewhere shared would remove, leaving nothing. Once a request's bytes are written to the daemon, **no path retries**: a lost response is indistinguishable from a dead daemon, and re-running `mail_send` sends twice. There is deliberately no round-trip deadline for the same reason — under that rule a timeout converts slowness into data loss.
- **One account only: the CLI refuses a multi-account config rather than picking the first.** Multi-account is out of scope by design (run one routine per `.env`), and silently choosing an account is the wrong way not to support it. `apple_accounts` stays available even under the refusal — it is the tool for seeing which accounts are configured, so refusing it too would leave no way to diagnose.

## Repository hygiene

`dist/`, `node_modules/`, and `.env` are gitignored and untracked — always run `npm run build` before `npm run serve` after touching `src/`. `.env.test` (real integration credentials) is gitignored too; only `.env.example` and `.env.test.example` (placeholders) are committed. Never read, print, or commit the contents of `.env`.

`.dockerignore` excludes `.env`/`.env.test` for the same reason `.gitignore` does, but the stakes are different: an image layer that ever contained a credentials file stays in that layer forever, retrievable by anyone who pulls the image, even after a later layer deletes the file. `Dockerfile`/`docker-compose.yml`/`Caddyfile` are themselves committed — they hold no secrets, only `env_file: .env` references and structure; the actual `PUBLIC_URL`/`ADMIN_PASSWORD_HASH`/`TOKEN_ENCRYPTION_KEY` values live solely in the untracked `.env`.
